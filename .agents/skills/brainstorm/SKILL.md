# Brainstorm（研究壁打ち）

研究相談を、既存文脈に基づく問い、仮説、比較案、次の判断へ整理する。
このスキルの成果物は探索記録であり、specでも実装許可でもない。内容が十分に固まり、
ユーザーが明示的にspec化を求めた場合は `research-spec` へ引き継ぐ。

## 責務境界

担当する:

- 研究文脈と直近Evidenceの読み込み。
- 問い、仮説、実験案、実装案、反例、比較軸の発散。
- 有力候補、保留、棄却寄り、未解決事項の区別。
- brainstormメモへの探索記録。
- `research-spec` が判断を再現できる引き継ぎ候補の作成。

担当しない:

- `specs/` への作成・更新・昇格。
- 研究コード、config、launcher、testの変更。
- 学習、HVP、大規模評価などの実験run。
- 合意前の案を実装可能な仕様として扱うこと。
- READMEやTODOの自動更新。

「この案でよさそう」「有力」「次に試す」は方向性の合意になり得るが、spec作成や
コード実装の許可にはしない。ユーザーが同じ依頼でspec化または実装まで明示した場合も、
まず `research-spec` のGateを通す。

## 原則

- 発散前に関連する研究文脈を読む。
- 分からないことを黙って補わない。複数の解釈が結果を変えるなら並べて確認する。
- 発散と収束を混ぜない。候補を広げてから、明示した評価軸で絞る。
- AI案への受け身化を避けるため、反例、別視点、未解決の問いを必ず含める。
- 未完成の思考を完成扱いしない。採用、候補、棄却、未決を区別する。
- brainstormメモは秘書室だけに保存し、プロジェクト配下へ `brainstorm/` を作らない。
- 既存ファイルへ追記するときはタイムスタンプを付け、内容を丸ごと上書きしない。
- 日付ベースのファイル操作前に今日の日付を確認する。

## 対象パス

```text
.company/secretary/notes/brainstorm/YYYY-MM-DD-topic.md
.company/secretary/todos/YYYY-MM-DD.md
.company/lab/projects/<project>/README.md
.company/lab/projects/<project>/meetings/*.md
.company/lab/projects/<project>/specs/*.md
.company/lab/projects/<project>/experiments/*.md
.company/lab/projects/<project>/references/*.md
```

`specs/` は重複や過去判断の確認のために読み取れるが、このスキルから書き込まない。

## 進行表示

通常は本文の前に短く現在地を示す。

```markdown
進行状況: 明確化中
完了: 対象特定 / 文脈読込
次: 発散
```

フェーズ変更時、保存前、ユーザーが迷いそうなときはフル表示を使う。

```markdown
進行状況:
- [x] 対象特定
- [x] 文脈読込
- [x] 明確化
- [ ] 発散 ← 現在
- [ ] 収束
- [ ] 構造化
- [ ] 保存
- [ ] spec引き継ぎ
```

短い相談で表示が会話を圧迫する場合は簡略化する。フェーズを戻す場合は、精度を
上げるために何を確認し直すかを一文で説明する。

## Workflow

### Phase 1: 対象特定

会話から次を特定する。分かっている項目は再質問しない。

- プロジェクト。
- 元TODOまたは相談の出発点。
- MTG由来か。
- 今回決めたいものが方針、仮説、実験、実装、調査のどれか。
- 成功したと言える状態と時間・計算資源の制約。

プロジェクトが未確定でも探索はできる。その場合は無理に既存プロジェクトへ結び付けない。

### Phase 2: 文脈読込

対象プロジェクトが分かる場合は、発散前に次を読む。

必須:

- `.company/lab/projects/<project>/README.md`
- 対象TODO、または今日・指定日のTODO
- `meetings/*.md` の直近1件

必要に応じて読む:

- 関連する `specs/` 最大3件。
- 関連する `experiments/` 最大3件。
- 関連するbrainstorm最大3件。
- `references/` はまず一覧だけを確認し、本文は必要なものだけ読む。

存在しない必須ファイルは捏造せず、未作成または該当なしとして前提に含める。

読み込み後は次の粒度で認識を示す。

```markdown
現在の文脈はこう理解しました。

- プロジェクト: ...
- 相談する問い/TODO: ...
- 直近の背景・Evidence: ...
- 決まっていること: ...
- 曖昧なこと: ...
```

### Phase 3: TODO変換

TODO起点では、そのまま作業項目として扱わず研究相談へ変換する。

```text
TODO
  -> 問い
  -> 仮説
  -> 実験案 / 実装案
  -> 比較・評価指標
  -> 次の判断
  -> spec引き継ぎ候補
```

### Phase 4: 明確化

重要な不足だけを確認する。

- 今回決めたいこと。
- 詰まりの原因。
- 既に試したこととEvidence。
- 利用できるデータ、モデル、コード、文献。
- 制約と成功条件。

複数解釈があり、どれを選ぶかで研究主張や実験設計が変わる場合は、選択肢と
トレードオフを示してユーザー判断を求める。探索を進められる非blockingな不確実性は
仮定として明示する。

### Phase 5: 発散

必要な観点から候補を広げる。

- 仮説、実験案、実装案。
- 比較対象、評価指標、調査方向。
- 反例、失敗条件、代替説明。
- 新規性、実現可能性、計算コストの異なる案。

要求されていない実装詳細を確定しない。ここでの単純案・複雑案はいずれも候補であり、
コードへ反映しない。

### Phase 6: 収束

評価軸を明示し、次へ分ける。

- 採用候補。
- 保留。
- 棄却寄り。
- 判断不能で追加Evidenceが必要。

主な評価軸:

- 研究上の問いへの寄与。
- 検証可能性と比較可能性。
- 新規性。
- 実現可能性と実験コスト。
- 失敗時に得られる情報。
- 既存baselineや過去実験への影響。

### Phase 7: 構造化

壁打ちの現在地を次へ整理する。

- 相談の出発点と中心となる問い。
- 採用または最有力の仮説・方針。
- 候補、保留、棄却案と理由。
- 判断に使ったEvidenceと評価軸。
- 未解決の問い。
- 次にユーザーが決めること。
- specへ引き継げる確定事項と、まだ不足する事項。

棄却案は削除せず、再検討条件があれば残す。ただし採用案と同列には置かない。

### Phase 8: 保存

壁打ちが一段落したら次へ保存する。

```text
.company/secretary/notes/brainstorm/YYYY-MM-DD-topic.md
```

同日・同topicがあれば、タイムスタンプ付きで追記する。

```yaml
---
date: YYYY-MM-DD
project: <project-name or null>
source_todo: <todo text or null>
topic: <topic>
status: exploratory
tags: [brainstorm, research]
---
```

本文には、読み込んだ文脈、出発点、問い、候補、仮説、実験・実装案、比較軸、
現在の方向性、棄却・保留、未解決事項、次アクション候補、関連ファイルを含める。

次アクションは候補として提示し、ユーザーが採用するまでTODOへ追加しない。

### Phase 9: research-specへの引き継ぎ

次が揃ってきたら、research-specへ渡せる材料を整理する。

- 中心となる問いまたは実装目的。
- 採用方向と、その根拠。
- 変更または実験のscope。
- 比較・評価方法。
- 主要な未決事項。

この段階ではspec readinessを判定せず、specも作成しない。ユーザーが明示的に
spec readiness確認またはspec化を依頼した場合は、次の引き継ぎ要約を `research-spec` へ渡す。

```markdown
# Research Spec Handoff

- 対象プロジェクト:
- 元TODO/依頼:
- 読み込んだ文脈とEvidence:
- 採用方向:
- 仮説または実装目的:
- 実験/実装候補:
- 比較対象・評価指標:
- 対象外:
- 保留・棄却案:
- 未決事項:
- 関連brainstorm・meeting・experiment:
```

この要約はspecではなく入力候補である。`research-spec` がread-only調査、曖昧性確認、
成功条件、互換性、再現性、承認状態を検査して初めて実装可能な契約になる。
