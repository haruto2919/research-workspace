# Notion公開ガイド

## いつ読むか

ユーザーが完成した壁打ち資料をNotionへ保存するよう明示した場合だけ読む。Markdown作成だけの依頼ではNotionへ接続しない。

## 保存先の確定

1. 利用可能なNotion連携と、接続中のworkspace identityを確認する。
2. 現在の依頼にNotion URL／IDがある場合は、その実行に限って明示先を使う。
3. 明示先がない場合は`config/notion-destination.local.json`を読み、`scripts/validate_destination.py`で検証する。
4. URL／IDを使って保存先の実体を取得し、通常ページかデータソースかを判別する。タイトル検索だけで保存先を決めない。
5. 設定を使う場合は、取得したworkspace名と保存先タイトルが設定値と完全一致することを確認する。
6. 保存先が不明、取得不能、権限不足、設定値不一致なら、新しい保存先を勝手に作らず停止する。
7. ホスト環境が書き込み直前の確認を要求する場合は、その規則に従う。

現在の依頼で使った明示先を設定ファイルへ自動保存しない。既定保存先の変更をユーザーが明示した場合だけ設定を書き換える。

## 通常ページへ保存する場合

`destination_type`が`page`なら、取得した通常ページを親として1件の子ページを作る。

作成前に親直下の既存ページを最後まで取得し、Markdownの最初のH1と完全一致するタイトルを確認する。子ページ一覧がページネーションされる場合は最終ページまで確認し、作成前の子ページID一覧を記録する。

## データソースへ保存する場合

`destination_type`が`data_source`なら、設定の`data_source_id`を使ってデータソースの新規行（ページ）を作る。親には次の形式を使う。

```json
{
  "data_source_id": "e8cad5f0-b4be-83a1-9c58-0724c9251ad1"
}
```

### スキーマの検証

書き込みのたびに`collection://<data_source_id>`を取得し、現在のスキーマを確認する。設定の論理名を次の型へ照合する。

| 設定上の役割 | 必要なNotion型 | 登録内容 |
|---|---|---|
| `title` | `title` | Markdownの最初のH1 |
| `created_date` | `date` | 保存日のローカル日付 |
| `keywords` | `multi_select` | 内容から選んだ既存選択肢 |

このSkillに設定済みの`研究ノート_DB`では、現在の対応は`名前`＝title、`作成日`＝date、`キーワード`＝multi_selectである。これは固定仕様とみなさず、毎回Notionから取得したスキーマを正とする。

プロパティが欠けている、名前が変わっている、型が異なる場合は書き込まず、設定値と実際のスキーマを報告する。未知のプロパティや選択肢を推測して作成しない。

### キーワードの選択

会話と完成Markdownから主要概念を抽出し、データソースの`multi_select`に現在存在する選択肢だけを0〜3件選ぶ。表記が意味的に明確に一致する場合だけ使い、新しい選択肢は作らない。適切な既存選択肢がなければ空配列にする。

`研究ノート_DB`で前回確認できた選択肢は`最適化`、`新規性`、`卒論`であるが、保存時に必ず最新一覧を再取得する。

### データソース内の重複確認

タイトル型プロパティに対して、作成予定タイトルの完全一致を問い合わせる。SQL形式の問い合わせを利用できる場合は、設定のデータソースIDとタイトルプロパティ名を使って次の形で検索する。

```sql
SELECT url, "名前"
FROM "collection://e8cad5f0-b4be-83a1-9c58-0724c9251ad1"
WHERE "名前" = ?
```

パラメータには作成予定タイトルを1件渡す。設定が別データソースを指す場合は、IDとプロパティ名を設定値へ置き換える。検索結果を文字列の部分一致で代用しない。

### プロパティの登録

`研究ノート_DB`へ保存する場合のプロパティは次の形式にする。

```json
{
  "名前": "Markdownの最初のH1",
  "date:作成日:start": "YYYY-MM-DD",
  "date:作成日:is_datetime": 0,
  "キーワード": ["既存選択肢"]
}
```

日付は実行環境のローカル日付を使う。本文にはローカルMarkdownから最初のH1だけを除いた内容を渡す。タイトルは`名前`プロパティに表示されるため、本文先頭へ同じH1を重ねない。

## 共通の重複方針

- 完全一致なし: 新規作成へ進む。
- 完全一致あり、指示なし: 作成も更新もせずスキップし、既存URLを報告する。
- 完全一致あり、更新指示あり: 更新対象のURLを示し、既存内容の扱いを確認してから更新する。
- バッチ内でタイトルが衝突: 該当資料を作成せず報告する。

## 作成結果が不明な場合

利用可能ならページ作成に冪等キーを使う。タイムアウトなどで結果が不明な場合は、作成操作を再送せず、最大2回の読み取り照合を行う。

1. 通常ページなら親直下を、データソースならタイトル完全一致クエリを再実行する。
2. 作成前には存在しなかった新規ページIDを抽出する。
3. 親ページIDまたはデータソースID、タイトル、本文の冒頭と末尾から作った指紋を照合する。
4. 条件を満たすページが1件だけなら作成済みと判断する。
5. 0件または複数件なら`作成結果不明`として停止し、作成操作を再送しない。

## 本文の登録

- Notionが対応するEnhanced Markdownまたはブロック形式を使う。
- 見出し順、本文、表、数式、コード、図のキャプションを維持する。
- 1 Markdownにつき1ページを原則とする。
- ローカルMarkdownにはH1を残し、Notion本文からは最初のH1だけを除く。その他の内容は省略しない。
- Notionの制限で表現を変更した場合は、完了報告に記載する。

## 画像の登録

1. 最終Markdownから参照される画像だけを対象にする。
2. 可能ならNotion連携の直接添付機能を使う。
3. URL経由の添付しか使えない場合は、外部公開する画像、公開先、用途、一時的な公開時間を説明し、公開直前にユーザーの同意を得る。
4. 同意後、実行ごとの専用一時ディレクトリへ画像だけを複製し、限定的な一時HTTPS転送を使う。
5. 転送URLが200を返すことと、Notion側のupload完了を確認する。
6. 全画像のuploadが成功し、Notion添付ブロックが揃うまでページを作成しない。1件でも失敗したらページ作成前に停止する。
7. 最終ページにはNotionが返した添付ブロックを使い、一時HTTPS URLを残さない。
8. 元画像とアップロード対象のSHA-256またはファイルサイズを記録する。

一時転送を使う場合は、ディレクトリ一覧を無効化し、Markdown、チャット本文、参照されていないファイルを公開しない。トンネルを確立できない場合は別の公開ホスティングへ無断でアップロードせず、画像付き公開を停止する。画像を省いたページを作る場合は、先にユーザーの了承を得る。

## 登録後検証

作成したページを取得し、少なくとも次を確認する。

- workspaceと親ページまたはデータソースが指定先に一致する。
- ページタイトルまたはタイトルプロパティが一致する。
- データソースの場合、作成日とキーワードが意図した値に一致する。
- 冒頭の要約と末尾の非空テキストが存在する。
- 見出しが必要数存在し、順序が大きく崩れていない。
- 表の数、行数、列数、ヘッダーが一致する。
- 添付画像数と画像のキャプションが一致する。
- 数式とコードがある場合、件数と本体が維持されている。
- ローカルMarkdownと画像が公開処理中に変更されていない。

検証に失敗しても、ページを自動削除・上書きしない。「成功」と報告せず、ページURLと不一致項目を報告する。

## Cleanup

成功・失敗にかかわらず、作業終了前に行う。

- 一時HTTPSトンネルを停止する。
- ローカルHTTPサーバーを停止する。
- listen portと関連processが残っていないことを確認する。
- 実行ごとのmanifestに記録された一時Markdown、画像コピー、upload mapだけを削除する。
- ユーザー向けの元Markdownと正式な図だけを残す。

正式なMarkdownや正式な図をcleanup対象へ含めない。広いディレクトリを対象とする再帰削除は行わない。

## Notion連携が使えない場合

完成したMarkdownと図をローカルへ保存して停止する。Notionへ保存したと報告せず、次を伝える。

- Markdownの保存場所
- Notion未保存であること
- 不足している接続または権限
- 設定ファイルから取得した保存先、または再開時に必要なURL／ID
